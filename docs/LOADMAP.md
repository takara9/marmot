# ロードマップ （気づきに応じて随時更新予定）

今回(2026/11/15)の自鯖缶での反応を振り返ると、以下の活用相談などがあった。

- Security GroupやOpen vSwitchによる動的な通信制御に関心を持つ人がいた。
- BGPによるKubernetesトラフィック制御を実験したい人がいた。
- 仮想マシンにMarmotをインストールして試したい人がいた。

つまり、Marmotに期待されているのは、単にクラスタを構成できることだけではない。

**安心して使える仮想化・ネットワーク基盤であること**だと感じました。


## **1. 今はクラスタの可用性より基礎品質**

Marmotの開発方針を次のように整理します。

### **私が考えるMarmotの本当の競争力**

ProxmoxやOpenStackと機能数を競う必要はない。Marmotの魅力は以下の部分である。

- 小さく始められる。
- 構成が分かりやすい。
- APIで操作できる。
- Kubernetes基盤としても使える。
- ネットワークを柔軟に制御できる。
- 障害から自動的に復旧できる。

これらを支えるのが基礎品質は、**新しい機能を10個追加するよりも、既存機能を安心して使えるようにする方が、企業ユーザーを獲得するうえで価値がある** と考えてロードマップを見直す。

Marmot 1.0への開発方針として、**機能の多さではなく、信頼性を最優先する**という基本に忠実になる。


## **Marmot 基盤強化ロードマップ**

**Phase 1：基礎品質の確立**

最優先で見直して品質を高めるべき事項

- Reconcile機能の堅牢化
- TLSによる通信の暗号化
- 認証・認可
- エラー処理とリカバリー
- ログ・監査機能
- データ整合性の確保

**Phase 2：実用的なインフラ機能**

- Security Group
- 仮想ネットワークの高度化
- BGP連携
- ストレージ管理の安定化
- バックアップ・リストア

**Phase 3：クラスタの高度化**

- コントロールプレーンの冗長化
- etcdの冗長化
- ControllerのHA
- 障害時の自動復旧
- ローリングアップデート

Phase 1を終えるまではクラスタ機能を捨てるのではなく、現在のクラスタ機能は、単一障害点を持つ構成として維持し、開発・検証に集中する。


## **2. Reconcile機能は徹底的に磨きたい**

これはMarmotの設計思想の中心であり、ProxmoxやOpenStackとの違いを明確にする部分なので、集中して考えたい。
例えば、次のようなケースを確実に処理できることなど。

| 発生する事象         | 期待する動作              |
| -------------- | ------------------- |
| VM作成中にDaemon停止 | 再起動後に処理を再開          |
| libvirtとの通信断   | 状態を再確認して再試行         |
| VMが外部から削除された   | 実際の状態と期待状態を整合       |
| ネットワーク作成失敗     | 中途半端なリソースを回収        |
| 設定変更           | 差分を検出して安全に反映        |
| 削除処理中に異常発生     | Finalizerによって後始末を継続 |


次の性質を品質目標に考える。

- 冪等性（Idempotency）
- 再実行可能性
- Eventually Consistent
- Finalizerによるリソース回収
- 状態遷移の一貫性
- 障害注入テスト

これは試験環境の構築を含めて、辛い対応になるけど、Daemonの停止と再起動があっても、最終的に期待状態へ収束することを重視する。


## **3. TLSとセキュリティは早めに整備する**

TLSは後から追加すると、APIやクライアント、証明書管理などに影響が広がります。

現在、Marmotは自己署名のTLS証明書を自動設定していません。そのため、早い段階で設計を固め、インストール時にTLS証明書が自動で用意される状態を目指します。

### 基本方針

- インストール時に、自己署名のTLS証明書（CA証明書とサーバー証明書）を自動で発行し、marmotdのREST APIで利用する。
- クライアント（mactl）には、インストール時に発行したCA証明書を配布し、サーバー証明書を検証できるようにする。
- 自己署名証明書は、評価用途および小規模環境向けの標準構成とする。
- 本番利用可能なクラスタでは、証明書と秘密情報の管理にVault/OpenBaoを利用できるようにする。

### 対象

| 対象              | 対応                                       |
| --------------- | ---------------------------------------- |
| REST API        | HTTPS化（インストール時に自己署名証明書を自動発行）           |
| Client - Daemon | TLS認証（CA証明書によるサーバー証明書の検証）             |
| Daemon間通信       | 相互TLS（mTLS）を検討                          |
| 証明書             | 発行・更新・失効                                 |
| 本番クラスタの証明書・秘密情報 | Vault/OpenBaoによる発行・保管・更新を選択可能にする       |
| API認証           | トークンまたはクライアント証明書                         |
| 権限管理            | 操作単位の認可                                  |

### 本番クラスタでのVault/OpenBao利用

本番利用可能なクラスタでは、自己署名証明書に代えて、Vault/OpenBaoを利用できるようにします。

- PKIシークレットエンジンで、サーバー証明書・クライアント証明書を発行し、更新・失効を管理する。
- 秘密情報（APIトークン、認証情報など）をVault/OpenBaoに保管し、設定ファイルへの直接記載を避ける。
- 自己署名証明書とVault/OpenBaoは設定で切り替えられるようにする。

TLSを導入するだけでなく、証明書の更新や期限切れへの対応まで考えておくことが大切と考えています。

## **4. 品質を測定できるようにする**

Marmotの品質を、感覚ではなくテスト結果で判断できるようにすること。
現在でも広範囲に、CIでテストを実施しているが、例えば、次のような品質基準を明確にする。

| 品質項目          | 目標            |
| ------------- | ------------- |
| Controller再起動 | 期待状態への自動収束    |
| API通信         | TLS必須         |
| リソース作成        | 冪等性を保証        |
| 障害発生          | 安全なリトライ       |
| リソース削除        | 後始末の完了        |
| E2Eテスト        | 主要操作を自動検証     |
| アップグレード       | 設定・データの互換性を検証 |
